# 技术方案 · 把工作流做成 TradeQuill 里的 Agent 应用

> 所属：[00 总览](需求-00-总览.md)　｜　实现 [01 选品](需求-01-选品.md)、[02 成本引擎](需求-02-成本与物流费率库.md)、[03 竞品跟踪](需求-03-竞品运营跟踪.md)、[04 补货与发货](需求-04-补货与发货.md) 的功能需求
> 版本 v0.14 · 2026-11-20 · 标记含义见总览；本文的技术选型除注明外都是【建议】

## 1. 一句话说明

**平台用确定性代码算数、存规则、管出处；Agent 只通过平台提供的工具取数、写文字、提建议；人在 TradeQuill 里审批。** Agent 换成谁，数字都一样，因为数字从来不是 Agent 算的（总览原则 2、3）。

## 2. 设计依据

本方案要满足的、已经在需求里定下的约束：

| 约束                                      | 来源                   | 对技术的要求                                               |
| ----------------------------------------- | ---------------------- | ---------------------------------------------------------- |
| TradeQuill 当每个成员的桌面端             | 总览第 10 节【已确认】 | 代码写进 TradeQuill（Tauri 2 + React 19 + Rust + SQLite）  |
| Agent 在各自电脑上跑，云端只存数据不跑 AI | 总览第 9 节【已确认】  | 服务器只跑数据库和 API，不跑 Agent；定时任务由在线电脑领取 |
| 不绑定 Claude，任意 Agent 接入口径一致    | 总览第 3 节【已确认】  | 对外提供 MCP；内置对话支持多家模型                         |
| 能在 TradeQuill 里直接和 Agent 对话       | 总览 P7【已确认】      | 内置一个 Agent 循环，和外部 Agent 共用工具                 |
| 规则、费率、阈值带生效期，不写死          | 总览原则 2、02         | 参数表 + 版本号；每次计算记录用了哪一版                    |
| 任何数字都有出处                          | 总览原则 3             | 数据源调用由平台代理并留存原始响应                         |
| 人做决定                                  | 总览原则 1             | 工具里没有"执行"类能力，只有"提建议"                       |

TradeQuill 现状（2026-11-19 读取 `~/Code/TradeQuill`）：

- Rust 后端通过 IPC 访问本地 SQLite（`rusqlite`），前端不能直接写 SQL。
- 依赖里**还没有**系统钥匙串、HTTP 客户端、MCP 相关库；电商数据接入只有调研文档 `docs/research/ecommerce-data-acquisition.md`。总览第 10 节说"可复用本地密钥保存方式"，实际要新做。
- `AGENTS.md` 写明"第一版维持单机、无 AI、无遥测"，需先按总览 10.1 在 TradeQuill 里提 Issue 改边界，才能开工第 5 节的 M3 以后。

## 3. 总体架构

```
┌──────────────── TradeQuill（每个成员电脑上一份）────────────────────────┐
│ 界面层（React）                                                         │
│   看板 · 选品简化表 · 报告 · 费率库 · 竞品跟踪 · 补货计划 · 待处理建议     │
│   右侧对话栏（P7）                                                      │
├────────────────────────── Tauri IPC ───────────────────────────────────┤
│ Agent 层                                                                │
│   内置 Agent：对话 + 后台写作任务；模型可配（Anthropic / OpenAI 兼容）    │
├─────────────────────────────────────────────────────────────────────────┤
│ 工具层：工具注册表（同一份定义两种出口）                                  │
│   ├─ 进程内调用 ← 内置 Agent                                            │
│   └─ 本地 MCP 服务 127.0.0.1 ← Claude Code / Codex / 其他外部 Agent      │
├─────────────────────────────────────────────────────────────────────────┤
│ 平台核心（纯 Rust，无 IO，无 AI）                                        │
│   单位换算 · 费率表查找 · 成本引擎 · 初筛规则 · 7盲2傻排除                 │
│   竞品变化识别 · 销量预测 · 补货与分批 · 资金曲线                          │
├─────────────────────────────────────────────────────────────────────────┤
│ 服务层：任务调度与加锁 · 证据库 · 次数与限流 · 审计日志 · 文档同步          │
│ 适配层：卖家精灵（MCP 客户端）· 1688 · 货代报价导入 · SP-API · 腾讯文档     │
├─────────────────────────────────────────────────────────────────────────┤
│ 存储：本机 SQLite（缓存 + 离线待发队列）  密钥：系统钥匙串                 │
└──────────────────────────────┬──────────────────────────────────────────┘
                               │ 同步（仅"亚马逊运营"模块的数据）
        香港服务器：API + Postgres（团队共享，只存数据，见 5.3）
```

**关键取舍：**

1. **核心层不碰 IO 和 AI。** 输入数据和参数表，输出结果和计算明细。这样最容易测，也保证"同样输入 → 同样数字"。
2. **工具只定义一次。** 内置 Agent 和外部 Agent 调的是同一个注册表，不会出现"对话里算的和 Claude Code 算的不一样"。
3. **平台代理所有付费数据源。** Agent 不直接连卖家精灵（见第 6 节）。
4. **能不用 AI 的环节就不用。** 每日快照、变化识别、补货重算都是平台定时任务，不需要模型（见 7.3）。

## 4. 平台核心

### 4.1 代码组织

- 在 TradeQuill 的 `src-tauri` 下建 Cargo workspace，新增 crate `amazon-core`（核心层）和 `amazon-ops`（服务、工具、适配层）；TradeQuill 原有代码不动。
- 需求文档留在本仓库；代码、Issue、PR 都走 TradeQuill 仓库的流程（总览 10.1）。

### 4.2 数值规则

- 金额用定点小数（`rust_decimal`），不用浮点；每个金额带币种，人民币和美元互换只在出结果时按"生效期内汇率"换算，并记录用的哪条汇率。
- 尺寸重量内部统一用 cm / g 存，按需换成 in / lb / oz；换算常量集中一处（1in = 2.54cm，1lb = 453.592g，1oz = 28.3495g）。
- FBA 体积重按 in³ ÷ 139；头程体积重按渠道除数（5000 / 6000 / 7000 / 不计抛），除数来自报价记录，不写死。

### 4.3 参数表与生效期

所有费率、阈值、规则都是同一种结构：

| 字段            | 说明                                                                    |
| --------------- | ----------------------------------------------------------------------- |
| 表名 / 键       | 如 `fba_fulfillment_fee`、`storage_monthly`、`screen_rule.monopoly_max` |
| 值              | 数值或 JSON（重量段、尺寸分段、售价档）                                 |
| 生效开始 / 结束 | 闭开区间；同一键的区间不能重叠，保存时校验                              |
| 状态            | 草稿 / 待确认 / 已生效 / 已作废；只有"已生效"参与计算                   |
| 来源            | 原件附件、链接、录入人、确认人、确认时间                                |
| 版本号          | 每次修改生成新版本，旧版本只读保留                                      |

- 计算函数签名统一是 `calc(输入, 参数快照) → (结果, 明细)`。服务层先按"计划发货日期 / 计算日期"取出参数快照再调用。
- 明细里列出每个数字用了哪条参数的哪个版本，界面上点数字就能看到（总览 P6）。
- 费率或规则更新后，服务层找出引用旧版本的结果，重新计算并列出变化最大的产品（02 第 2 节）。

## 5. 存储与团队同步

### 5.1 主要数据表

| 类别 | 表                                                                  | 要点                                                                          |
| ---- | ------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 任务 | 任务、任务运行记录                                                  | 状态机按各模块看板状态；运行记录含 Agent、开始结束、消耗、异常                |
| 证据 | 数据源调用记录（证据）                                              | 数据源、工具名、参数、原始响应、响应哈希、时间、电脑、Agent、消耗次数         |
| 选品 | 候选产品、指标值、简化表行、报告（带版本）、评审                    | 每个指标值指向一条证据或一条计算记录                                          |
| 成本 | 参数表（4.3）、报价、报价原件、计算记录                             | 计算记录存输入、参数快照版本、输出、明细                                      |
| 竞品 | 对标关系、每日快照、Listing 指纹、事件、打法时间轴                  | 快照只存平台解析后的字段 + 证据引用                                           |
| 补货 | 采购批次、自己仓库库存（待贴标 / 可发货）、补货批次、货件、贴标任务 | 状态按 04 第 9 节                                                             |
| 建议 | 待处理建议                                                          | 类型、参数、依据（证据 / 计算记录）、状态、决定人、理由、7 天和 14 天回看结果 |
| 对话 | 对话、消息                                                          | 默认仅自己可见，不同步；"附到任务"后才同步                                    |
| 管理 | Agent 身份、用量账本、审计日志                                      | 审计日志只追加                                                                |

- 主键用 UUIDv7（离线也能生成且按时间有序）；每行带 `version`、`updated_by`、`updated_at`、`deleted`。
- TradeQuill 原有的客户、询盘、报价等个人数据不进这些表，也不同步（总览 10.1）。

### 5.2 同步方式

- **云端数据库是团队数据的权威来源**，本机 SQLite 是缓存。
- 写操作先进本机"待发队列"，联网后按顺序推送；推送带上读取时的 `version`，云端发现版本不一致就拒收，本机保留双方版本并提示人选择，不静默覆盖（总览 10.1）。
- 云端变更由 API 通过 WebSocket 推送到在线成员，目标是秒级（总览第 11 节）。
- **任务领取在服务器上原子完成**：API 在数据库事务里执行一条带条件的更新（状态为"待领取"或租约已过期 → 改为本机领取，租约 15 分钟），运行中定期续租；电脑崩溃后租约过期，别的电脑可接手。离线时不能领取新任务。
- 用量账本和限流也在云端协调（第 6 节），否则多台电脑会各算各的。

### 5.3 云端：自购香港服务器【已确认 2026-11-19】

团队自己买一台香港服务器，跑 Postgres 和一个薄 API；服务器上不跑任何模型，符合总览第 9 节"云端只存数据、不跑 AI"。

**为什么选它（2026-11-19 比较过的方案）：**

| 方案                                         | 结论                                                                                            |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Supabase 托管                                | 登录、同步现成，Pro 约 $25 / 月；服务器在境外，国内访问需实测；免费版闲置一周会暂停             |
| Cloudflare（D1 + Workers + Durable Objects） | 约 $5 / 月；登录、推送要自己写；国内访问需实测                                                  |
| **自购香港服务器【已选】**                   | 国内访问通常稳定、无需 ICP 备案、数据在自己手里；代价是要自己写 API 并负责运维和备份（第 9 节） |

**服务器上跑什么：**

- **Postgres**：团队共享数据的权威来源；只监听本机，不对公网开放端口。
- **API 服务**：Rust + axum，和 TradeQuill 共用 `amazon-core` 里的数据结构和校验，避免客户端和服务端口径不一致。负责：
  - 登录：账号密码（密码用 argon2 哈希），签发有过期时间的令牌；负责人可停用成员；
  - 同步接口：按 5.2 推送和拉取，版本冲突拒收；
  - 实时推送：WebSocket，数据变更后推给在线成员；
  - 任务领取租约、全队数据源限流计数、用量账本：在数据库事务里原子完成；
  - 权限：负责人才能改规则、费率和确认报价（第 9 节）。
- **反向代理**：只开放 443，自动续期 HTTPS 证书。

**配置【建议】：** 2 核 4G、40–80 GB 磁盘起步；原始证据响应量大时优先压缩或单独放对象存储，不急着升配置。具体厂商和价格购买时再定。

**部署与备份【建议】：**

- API 和 Postgres 用 Docker Compose 部署，配置和部署脚本放进 TradeQuill 仓库，密钥不进仓库。
- 每天自动 `pg_dump` 一份，传到**这台服务器以外**的对象存储，保留 30 天；每月做一次恢复演练，在另一台机器上还原并核对行数。
- 服务器只允许 SSH 密钥登录，关闭密码登录；开防火墙；系统安全更新定期打。
- 加一个简单的在线监测，API 不可用时通知负责人；TradeQuill 在服务器不可用时照常离线使用（5.2）。

## 6. 数据源适配：平台代理卖家精灵

现在的做法是 Claude Code 直接连 `ss_mcp`，由 `.claude/skills/sellersprite/SKILL.md` 约束口径，数据存到 `local/选品数据/` 下的 Excel。原型阶段够用，但"省着用次数""任何数字都有出处"只能靠提示词，换个 Agent 就失效。

**改为：** TradeQuill 作为 MCP 客户端连卖家精灵，对 Agent 只暴露平台包装后的工具 `source_query`。

```
Agent ──source_query(工具名, 参数)──▶ 平台
                                     ├─ 1 工具名在白名单内？参数合法？
                                     ├─ 2 查缓存：同参数、有效期内（默认 7 天）→ 直接返回
                                     ├─ 3 预估消耗；超当日 / 当月限额 → 拒绝并提醒负责人
                                     ├─ 4 云端令牌桶：全队每分钟 ≤ 40 次，超了排队
                                     ├─ 5 调用卖家精灵，原始响应存为一条证据
                                     └─ 6 返回：数据 + 证据编号
```

- Agent 提交候选产品、快照时**只引用证据编号**，关键字段（价格、销量、BSR、重量尺寸、评分）由平台按工具类型从原始响应里解析，不采信 Agent 抄写的数字。解析器按卖家精灵工具逐个写，口径陷阱沿用 sellersprite 技能里的规则。
- 卖家精灵密钥只存在负责人授权过的电脑的钥匙串里；外部 Agent 的配置里不再出现密钥。
- 其他数据源（1688、SP-API、Keepa 等）按同一接口接入：白名单、缓存、限额、证据、解析器。SP-API 第二期接入，授权令牌同样只存本机钥匙串。
- **过渡期**：M2 之前继续用现有技能直连；M2 上线后，外部 Agent 的说明改为只用 `source_query`，并移除直连配置。

## 7. Agent 层

### 7.1 工具清单（MCP 与内置共用）

把 01 F6、02 第 7 节、03 第 6 节、04 第 10 节的接口能力合并成一份。按权限分三级，Agent 身份可单独限制级别。

| 级别 | 工具                                               | 说明                                                                      |
| ---- | -------------------------------------------------- | ------------------------------------------------------------------------- |
| 读   | `task_claim`                                       | 领一个任务；返回任务说明书（7.2）和租约                                   |
| 读   | `rules_get`                                        | 当前规则、阈值、报告模板及版本                                            |
| 读   | `cache_lookup`                                     | 查平台已有的 ASIN / 关键词 / 类目数据                                     |
| 读   | `source_query`                                     | 代理数据源查询（第 6 节）                                                 |
| 读   | `cost_estimate`                                    | 试算成本矩阵；也用于试算调价、优惠的利润影响                              |
| 读   | `quote_get`                                        | 某渠道、某日期有效的头程报价                                              |
| 读   | `product_get` / `competitor_get` / `inventory_get` | 产品、竞品、库存全景（只读）                                              |
| 读   | `replenish_plan_get` / `replenish_simulate`        | 平台算出的补货方案；按给定批次试算                                        |
| 提交 | `candidates_submit`                                | 提交候选产品（引用证据编号）                                              |
| 提交 | `price_1688_submit`                                | 采购价、链接、起订量、阶梯价；第一期多为人工或 Agent 从页面摘录，标注来源 |
| 提交 | `report_section_submit`                            | 报告某一部分的文字分析和六项打勾理由                                      |
| 提交 | `snapshot_submit` / `timeline_submit`              | 竞品快照补充字段、打法时间轴文字                                          |
| 提交 | `quote_draft_submit`                               | 报价识别草稿，只进"待确认报价"                                            |
| 提交 | `task_progress` / `task_fail`                      | 进度、异常、断点信息                                                      |
| 建议 | `suggestion_create`                                | 结构化建议（类型、参数、依据）；进「待处理建议」等人审批                  |

- **没有**改价、下单、建货件、确认报价、删除数据的工具（总览 P7、04 第 10 节）。
- 每个提交类工具都校验：必填的证据引用、字段范围（如售价 > 0、重量合理）、任务租约有效；不通过就返回具体原因，让 Agent 改了再交。
- 用量登记由 `source_query` 自动完成，不再需要 Agent 主动"登记次数消耗"。

### 7.2 任务说明书：流程定义放在平台里

`task_claim` 返回的不只是任务参数，还有这一步的说明书：

| 字段       | 例子（选品"撒网初筛"）                                                             |
| ---------- | ---------------------------------------------------------------------------------- |
| 目标       | 从类目节点 X 拉取候选，排除 7 盲 2 傻，提交候选                                    |
| 步骤       | 1 `rules_get` 2 `cache_lookup` 3 `source_query(asin_list …)` 4 `candidates_submit` |
| 允许的工具 | 上面四个 + `task_progress`                                                         |
| 次数预算   | 本任务最多 N 次                                                                    |
| 输出要求   | 每个候选必须带证据编号；六项打勾每项一句理由                                       |

- 说明书和规则一样带版本，由负责人在 TradeQuill 里维护。
- 这样外部 Agent 本地只需要一份很短的通用说明："连 TradeQuill MCP → 领任务 → 照说明书做"。换 Agent 不用重写提示词，流程改了也只改平台一处。

### 7.3 哪些环节需要模型

| 环节                                       | 谁做                          | 要不要模型                                 |
| ------------------------------------------ | ----------------------------- | ------------------------------------------ |
| 撒网拉数据、解析指标、硬指标、成本         | 平台（数据由 Agent 发起查询） | 发起查询可由 Agent，也可由平台按规则直接跑 |
| 六项打勾理由、报告分析段落、评论好差评提炼 | Agent                         | 要                                         |
| 报价图片 / PDF / 微信文字识别成草稿        | Agent（多模态）               | 要                                         |
| 竞品每日快照、变化识别                     | 平台定时任务                  | **不要**                                   |
| 打法时间轴叙述、周总结、模仿建议           | Agent                         | 要                                         |
| 补货每日重算、预警                         | 平台定时任务                  | **不要**                                   |
| 补货建议的一句话解释                       | Agent                         | 要（可选）                                 |
| 对话问答                                   | 内置 Agent                    | 要                                         |

不需要模型的定时任务由 TradeQuill 自己领取执行（总览 9.2），不依赖外部 Agent 是否开着。

### 7.4 内置 Agent

- 在 Rust 后端实现一个工具调用循环：发消息 → 模型请求调用工具 → 进程内执行 → 结果回传 → 直到给出回答。
- 模型接口做两个适配器：Anthropic Messages API、OpenAI 兼容接口（覆盖 DeepSeek 等）。模型和密钥在 TradeQuill 的 AI 服务设置里配（复用 TradeQuill #18 的规划），密钥存钥匙串，只在后端使用。
- 对话时自动带上当前页面上下文（产品、报告、补货批次的编号和摘要），不用复制粘贴（总览 P7）。
- **防编数字**：回答里出现的数字，平台检查它是否出现在本轮工具结果里；能对上的显示为可点开来源的链接，对不上的标"未核实"。
- 后台写作任务（报告段落、周总结）也由内置 Agent 按说明书执行；成员也可以改用外部 Agent 领同一类任务。
- 每次调用记录模型、输入输出 token、费用估算，计入用量（总览 P7"用量"）。

### 7.5 外部 Agent 接入

- MCP 服务只监听 `127.0.0.1`，用 Streamable HTTP；实现用官方 Rust SDK（`rmcp`）。
- 每个外部 Agent 在 TradeQuill 里登记，生成独立令牌（存钥匙串，界面只显示一次），可单独停用；所有调用写审计日志（总览 P3）。
- TradeQuill 提供"复制接入配置"按钮，生成 Claude Code、Codex 的配置片段（令牌用环境变量引用，不写进配置文件）。

### 7.6 不可信内容

竞品标题、五点、评论、货代发来的图片和文字都是外部内容，可能夹带"指令"。处理方式：

- 传给模型时放在明确的"数据"段落里，系统提示说明这些内容不是指令。
- 根本防线是工具权限：Agent 本来就没有执行类工具，被诱导也只能多提交一条要人审批的建议。

## 8. 输出与集成

- **腾讯文档**：平台 → 文档单向同步，写入失败进重试队列；接口能力【待调研】，不行就降级为导出 Excel（总览 P5、第 13 节）。
- **通知**：用 TradeQuill 已有的系统通知插件；手机推送【待确认】（总览第 12 节）。
- **标签与装箱单 PDF**：04 第 7 节的贴标任务由后端生成。

## 9. 安全

- 密钥（卖家精灵、SP-API、1688、腾讯文档、模型 API、Agent 令牌）全部存系统钥匙串（新增 `keyring` 依赖），不写文件、不进日志、不同步云端（总览第 11 节）。
- 前端只能调用明确的业务 IPC，不暴露任意 SQL 或文件路径（沿用 TradeQuill `AGENTS.md` 的约定）。
- 服务器由 API 按成员登录和角色校验权限；负责人才能改规则、费率和确认报价。服务器自身的加固和备份见 5.3。
- 审计日志记录人和 Agent 的每次写操作，只追加不修改。

## 10. 验证方式

| 层           | 怎么验证                                                                                                                                                                                  |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 核心层       | 单元测试 + **黄金样例**：用 `local/选品数据/` 里已有的采购与利润表、`local/参考资料/物流报价/` 里的货代报价，人工核对一批产品的成本，引擎结果必须一致；FBA 费率用卖家后台费率页的官方例子 |
| 参数表       | 生效期重叠、缺失、过期时的行为测试                                                                                                                                                        |
| 工具层       | 每个工具的契约测试：合法输入、缺证据、越权、租约过期                                                                                                                                      |
| 数据源代理   | 用录制好的卖家精灵响应做解析器测试，不在测试里消耗次数                                                                                                                                    |
| Agent 可替换 | 同一个选品任务分别让两个不同模型跑，平台算出的数字必须完全一致，只有文字不同（01 第 2.2 节"Agent 可替换"）                                                                                |
| 同步         | 两台电脑同时改同一条、断网写入后恢复、领取任务时电脑崩溃                                                                                                                                  |
