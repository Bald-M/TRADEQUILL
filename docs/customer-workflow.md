# 客户与跟进工作流

本文记录 schema 2 引入的客户业务主线、字段约束和第一版边界。业务数据只保存在应用自有 SQLite 中，并只通过类型明确的 Rust IPC 读取或写入。

## 客户与询盘

- 客户姓名必填；公司、邮箱、电话、国家或地区、来源和备注可选。邮箱填写后必须满足基本地址格式。
- 新询盘必须关联已有客户。为同一客户追加询盘不会创建第二份客户档案。
- 询盘来源、国家或地区是去除首尾空白后的自由文本；筛选使用完全匹配，不预设平台或 ISO 国家清单。
- 每条询盘可记录 1–20 个意向产品。界面接受逗号、中文逗号、顿号或换行分隔，并合并不区分英文大小写的重复项。
- 跟进阶段固定为：新询盘、已联系、已报价、样品中、已成交、暂缓。
- 第一版不开放客户或询盘删除。这里的“归档”指将询盘保存为可追溯记录；历史关联不会被级联清除。需要删除、恢复或合并重复客户时应先另行定义数据恢复策略。

## 报价记录

- 报价归属于客户，可不关联询盘；关联时只能选择该客户自己的询盘。
- 日期、产品或内容、非负金额和币种必填。支持 USD、CNY、EUR、GBP、JPY，金额最多两位小数并以整数最小单位存储。
- 同一客户或询盘可创建多条报价，按日期稳定展示。一次商业报价的修订应创建新记录；“编辑”只用于更正录入错误，不将覆盖后的值描述为完整修订历史。
- 报价记录不生成或发送正式报价单，也不进入订单、收款或发票流程。

## 样品进度

- 样品记录包含产品、正整数数量、申请日期、备注，以及可选的同客户询盘。
- 阶段按 `已申请 → 准备中 → 已寄出 → 已签收 → 已完成` 前进；未完成阶段可以转为“已取消”。跳级、从终态继续或日期早于上一条进度都会被拒绝，且不会产生部分写入。
- 每次阶段变化追加一条不可覆盖的历史事件。尚未进入后续阶段时可以更正申请日期；进入后续阶段后通过进度备注记录更正，避免改写历史。
- 已寄出后可手动记录承运方和物流单号。该字段不是实时物流状态，不调用承运方 API。

## 跟进、日历与提醒

- 跟进任务必须关联客户，可选关联该客户自己的询盘。改期会更新同一任务；完成后可重新标记为未完成。
- 日期时间按当前设备的本地时区保存为本地日历值。应用每次启动、重新获得焦点及运行中的定期检查都会重新计算今日和逾期状态。
- 每日 09:00 后，如存在今日或逾期未完成任务，应用尝试发送一次系统摘要通知；发送成功后以本地日期去重。完成任务不会进入提醒，改期任务只按新日期参与后续计算。
- 系统通知权限被拒绝或发送失败时，界面显示原因，应用内今日/逾期列表仍然可用；失败不会记录为已发送。
- TradeQuill 完全退出后不在后台运行，因此不能承诺退出状态下发送提醒。重新打开应用时会补算到期任务；休眠恢复后通过窗口焦点或定期检查补算。

## 数据迁移与安全

- schema 1 到 schema 2 的全部建表和索引创建在同一 SQLite 事务中完成。迁移保留 `app_metadata` 和已有数据，重复启动不会重建或清空记录。
- 应用拒绝打开高于当前支持版本的数据，不执行降级覆盖。
- 前端没有任意 SQL、数据库路径或文件系统访问能力。每类写入都有独立命令，客户与询盘关联在事务内再次校验。
- 第一版继续保持个人单机、本地优先、无 AI、无云同步和无遥测。
